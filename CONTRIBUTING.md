# Contribution Guide

`AGENTS.md` and `CLAUDE.md` link to this doc, there's no need to read them.

This project is a POC with no users. Don't worry about backwards compatibility, or migration concerns. 
Don't document changes in behavior, assume the reader reads the doc for the first time and has no prior context.

If a behavior is documented it must be implemented in code. If a behavior is implemented in code (or observed), it must be documented. The docs (and the UX) matter more than the code.

The reference docs (under `docs/reference`) are the technical specification for the product components. The Manual is the entrypoint for users and delegates to reference docs for details. The CLI and general UX is defined in the manual. The Cheat Sheets (under `docs/cheat-sheets`) are not considered source of truth, they are derived from canonical docs.

## Documentation

Documentation is written in Markdown. Use simple, succinct, normative, technical style.

Every paragraph should discuss one topic. It's ok for a paragraph to have one short sentence if it concludes the topic.

Avoid styling (bold, underline, italics) if possible.

When using bulleted lists, use `-` instead of `*`.

Don't break lines at 80 characters.

Avoid long sentences.

Consider the existing semantic structure of the document you're editing (i.e headings hierarchy) and try to follow it.

Refactor docs like code. Don't repeat the same documentation in separate places, find or define the shared definition and refer to it.

If a document has a commend that starts with "agents:", read it and follow its instructions. For example `<!-- AGENTS: don't touch this doc. -->`

## Orientation

Agents development lifecycle:

1. Project - contains agent definition file (yaml) and optionally related assets.
2. Package Directory - directory with a package manifest and all materialized assets. 
  1. It is runnable, but it's rarely used directly. It's considered an intermediary artifact.
3. Package - a `tar.gz` archive of the package directory.
  1. It is runnable. It is considered the primary build artifact and the stable form for distribution.

The Run command accepts any form (project, package dir, package) and will automatically build a package to run it.
When running an agent, the run command compiles the portable package into a target-specific harness config, and runs the harness.

## Terminology

This section is the normative terminology for the project. It governs the docs, the code, CLI output, and commit messages. Another document may restate a definition if needed, but it must not conflict with this section and must not introduce new terms not defined here. To change a term, change it here first, then update other occurrences.

### Build

- **agent project** (or **project**): the directory containing the agent definition file and local source assets.
- **agent definition file**: the YAML definition in an agent project.
- **agent assets**: the resources that compose the agent definition, for example prompt, system prompt, skills.
- **assets sources**: the origin and resolution strategy for assets that are loaded from external locations.
- **assets resolution**: the process of determining the final map and accurate version reference of assets sources.
- **assets materialization**: the process of fetching all external sources and organizing them for consumption.
- **package directory** (or **package dir**): a generated, portable directory containing a package manifest and materialized assets, but no provisioned executables.
- **package**: a `.tar.gz` archive of the package dir. This is the deterministic build artifact for distribution.
- **package manifest**: the `manifest.json` file at the package-dir root. It is the complete generated agent definition and its run-time requirements. It is not an agent definition file.

### Run

- **run**: one agent invocation.
- **run mode**: how the agent interacts with the user, what protocols and interaction mode.
- **one-shot agent**: a non-interactive, unattended agent that has a built-in prompt and runs to completion.
- **run profile**: user preferences for running an agent (for example, the harness, LLM, and environment settings).
- **execution target** (or **target**): the resolved `{harness, provider, model}` tuple.
- **workspace**: the working directory the harness is executed in.
- **harness adapter**: the mapping from a target-agnostic package to a target-specific harness configuration.
- **harness configuration** (or **harness config**): the per-run harness configuration and command generated by the harness adapter.

## Testing

Run the unit and contract tests for every change:

```bash
make test
```

These tests do not require Docker, network access, or installed harnesses.

The integration tests require a running Docker daemon. Run the target that covers the change:

```bash
make harness-integration-test
make integration-test
```

- `make harness-integration-test` tests the maintained container recipes with the real harnesses and mock LLM.
- `make integration-test` runs `make harness-integration-test`.

The integration tests remove their image tags after each run. Retain the tags for debugging with:

```bash
PANDRA_KEEP_INTEGRATION_IMAGES=1 make integration-test
```
